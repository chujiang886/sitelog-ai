# BOIP Phase 3.9.15 — Provider Acquisition / Lock / Cache Strategy (T3 / T4)

- **Problem**: `terraform init` against `infrastructure/staging/*.tf` fails because the
  `tencentcloudstack/tencentcloud` provider binary + checksum are hosted on `github.com`,
  which the agent sandbox egress proxy **black-holes** (see `phase3.9.15_provider_init_root_cause_report.md`).
- **Goal**: A fail-closed, reproducible provider acquisition path that does NOT require
  real apply and does NOT depend on the sandbox's blocked GitHub egress.

---

## 1. Constraints (fail-closed)

1. No real `terraform apply` is performed by AI in this phase.
2. No provider binary is downloaded into the sandbox (GitHub egress is blocked anyway).
3. The `.terraform/` and `.terraform.lock.hcl` artifacts generated by a real operator are
   **never committed** to the repository (they are environment-specific and may carry
   machine-local paths).
4. Provider versions are pinned in `versions.tf` (`>= 1.81.0`) — the lock file must
   reproduce the exact resolved version (currently observed `v1.83.23`) on a reachable host.

## 2. Strategy A — Private / Mirror Provider Installation (RECOMMENDED)

Configure a reachable provider mirror so the sandbox (and CI) can fetch the binary without
GitHub egress:

```hcl
# ~/.terraformrc  (or $TF_CLI_CONFIG_FILE)
provider_installation {
  network_mirror {
    url = "https://<reachable-mirror-host>/terraform/providers/"
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}
```

The mirror is populated out-of-sandbox (real operator, egress-enabled):

```bash
# on an egress-enabled machine
terraform providers mirror -platform=linux_amd64 \
  -platform=darwin_amd64 infrastructure/staging/
# -> produces a vendor dir + .terraform.lock.hcl
```

Then in-sandbox (or CI): `terraform init -plugin-dir=<vendor>` — no GitHub egress needed.

## 3. Strategy B — Offline Cache Copy

A real operator runs `terraform init` on an egress-enabled machine, then copies
`.terraform/providers` and `.terraform.lock.hcl` into the target environment. The sandbox
then runs `terraform init -plugin-dir` against the copied cache. This is fully offline.

## 4. Strategy C — Vendored Lock File + Manual Checksum Trust (fallback)

If a mirror is unavailable, the operator generates `.terraform.lock.hcl` from a trusted
source and commits it **only if** the org policy allows vendored locks. BOIP policy: the
lock file is **environment-specific and must NOT be committed by AI**; it is supplied by a
human operator as part of the real onboarding bundle.

## 5. Lock / Cache Integrity (T4)

- The `.terraform.lock.hcl` MUST record the exact provider version and the official
  SHA256SUMS signature from the registry (not GitHub) when reachable, or from the mirror.
- Any cache used in-sandbox is validated by `terraform init -check` before plan/apply.
- The scanner (`plan_safety.PlanSafetyScanner`) runs independently of provider availability
  and already returns **SAFE** on the committed IaC (no hardcoded secret, no public DB,
  no `0.0.0.0/0`, no disabled encryption, no destructive op, no production-targeting value).

## 6. Disposition for Phase 3.9.15

- T3 (acquisition strategy): defined above (Strategy A recommended; B/C fallbacks).
- T4 (lock/cache): template described; **the actual lock file is produced by a human
  operator out-of-sandbox** and is intentionally NOT committed by AI.
- Consequently T5 (init) = FAIL, T6 (validate) = BLOCKED, T7 (plan) = BLOCKED in-sandbox,
  all recorded honestly. Real provider availability is a **human / out-of-sandbox**
  prerequisite, not a software-phase closure criterion.
