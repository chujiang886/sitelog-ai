## 二、三方案现状分析

"三方案" = `candidates` 数组中的 **3 个候选（D1/D2/D3，按推荐度降序）**。依执行计划 S2A 目标，三方案对应 **经济 / 舒适 / 高性能** 三种原型（archetype）。

### 2.1 三方案当前专业化水平

| 字段 | 当前形态 | 专业化缺口 | 当前可信等级 |
|---|---|---|---|
| `opening_type` | 自由类别（推拉窗/平开窗…） | 无风环境适配依据 | Level 0 inferred（`pending_verification`） |
| `frame_material` | 类别（断桥铝/塑钢…） | **无型材壁厚/系列** | Level 0（`pending_verification`） |
| `glass_type` | 类别（中空/Low-E/夹胶） | **无玻璃厚度/安全等级** | Level 0（`pending_verification`） |
| `dimensions_hint` | 自由文本 | 无结构化尺寸阈值 | Level 0（`pending_verification`） |
| `estimated_cost_tier` | 三档文字 | 非真实成本 | Level 0（`pending_verification`） |
| `pros` / `cons` / `rationale` | 定性描述 | 部分可引用环境事实，但未标注来源 | Level 0 / 部分 Level 1 |

### 2.2 专业化目标（不填值）

三方案专业化 = 让每个候选在**不杜撰数值**前提下，达到：

1. **环境感知**：消费 2.2.1 实测字段（若 measured，pending_verification）作为约束条件（如高风压区→优先内开），推理过程显式标注依据等级。
2. **结构化阈值占位**：为 `frame_material` / `glass_type` / `dimensions` / `cost` 预留"阈值引用槽位"（指向 §三 的阈值 ID），数值本身仍 `pending_verification`，待专家签字后由机制消费。
3. **三原型差异化**：经济/舒适/高性能各自在成本—舒适—性能三角上明确取舍维度，差异化 `rationale`。
4. **语义对齐**：无论 LLM 是否成功，凡含 Level 0 字段即 `pending_verification=True`（修正 P1）。

> 注：三方案专业化**不包含**任何真实工程计算；`engineering_enabled=false` 红线不变。

## 三、pending_verification 阈值盘点方案

**方法**：

1. **静态扫描**：对 `agents/**` 与 `agents/config.yaml` 做 `pending_verification` / `threshold` / 领域词（风压/楼层/壁厚/玻璃厚度/评分权重）全文检索，提取所有"结论性或配置性参数"。
2. **人工复核**：逐一对扫描命中项判定"是否为工程阈值/业务参数"，剔除误报（如 prompt 中的禁用声明）。

## 四、阈值确认清单设计

**交付物**：《阈值确认清单》（`docs/thresholds/confirmation_checklist.md` 或生成于 `agents/design/thresholds/`），供行业专家逐项签字。

### 4.1 清单结构（每行 = 一个阈值）

| 列 | 含义 | 本设计填充？ |
|---|---|---|
| 阈值 ID | 引用 §三 的稳定 ID | 自动带出 |
| 参数名 | 人类可读名称 | 自动带出 |
| 用途说明 | 该阈值影响哪个设计决策 | 自动带出（模板文案） |
| 影响范围 | 影响哪些候选字段 / Agent | 自动带出 |
| 建议来源 | 规范/标准/专家经验（指向，不取值） | 自动带出（占位） |
| **建议取值区间** | 专家填 | **本设计留空（`pending_verification`）** |
| **专家签字** | 专家署名 | **留空，待专家** |
| **签字日期** | ISO8601 | **留空，待专家** |
| 状态 | `pending` / `verified` / `rejected` | 默认 `pending` |

### 4.2 生成机制（设计）

- 实施阶段提供 `scripts/gen_threshold_checklist.py`：读取 §三 盘点表（单一数据源）→ 渲染 Markdown 清单。
- 清单与代码同源，避免"清单与实际 drift"（风险 R5）。
- **拒绝/暂缓路径**：专家可对单项标 `rejected` / `deferred`，该类阈值维持 `pending`，不影响其他项转正。
- **一票否决语义**：任一阈值未获 `verified` 签字 → 对应候选字段保持 `pending_verification=True`。

> 本设计文档**不生成**清单实体文件、不填写任何签字列；仅设计其结构与生成方式。

## 五、verified_by / verified_at 机制设计

**目标**：为"已签字阈值"提供可机读、可审计的存储与消费机制，且**未经签字绝不被代码当作真实值使用**。

### 5.1 存储模型（设计）

新增 `agents/design/thresholds/verified.json`（或 `config.yaml::design_thresholds` 段），schema 示例（**value 留空，本设计不填**）：

```json
{
  "schema_version": 1,
  "thresholds": {
    "D-TH-01.frame_wall_thickness": {
      "value": null,
      "unit": "mm",
      "verified": false,
      "verified_by": null,
      "verified_at": null,
      "source_ref": "（待专家签字填入规范/标准号 pending_verification）",
      "applies_to_scheme": ["economy", "comfort", "performance"]
    }
  }
}
```

### 5.2 加载器（设计，沿 2.2.1 模式）

- 新增 `agents/config_loader.py::load_verified_thresholds(config_path)`（与 `load_environment_data_config` 对称）。
- 缺省/文件不存在 → 返回空 dict（等价全 `pending`），**合入即零行为变化**。

### 5.3 消费与语义（与 ADR-2.2.1 §7 对齐）

- DesignAgent 加载已签字阈值；对 `verified=true` 且 `verified_by`/`verified_at` 俱全的阈值，其对应候选字段 `field_provenance[field]="verified"`，并在该字段层面不再 `pending`。
- 顶层 `pending_verification` = `any(field_provenance[k] != "verified" for k in KEY_FIELDS)`（KEY_FIELDS 待实施定，建议含 `frame_material`/`glass_type`/`dimensions_hint`/`estimated_cost_tier`）。
- **红线锁（双重）**：
  1. `verified=false` 或缺失 `verified_by`/`verified_at` → 该字段**禁止**以任何数值写入候选，保持 `pending_verification`。
  2. CI 第 7 步（`check_fabrication`）扩展：识别"无 `verified` 元数据却硬编码为真实数值的阈值" → 扫描失败（防伪造转正）。

> 本设计**不写入**任何 `verified=true` 记录、不填任何 `value`、不出现真实 `verified_by/verified_at`。

## 六、专家审核流程设计

**外部依赖**：行业专家排期（TD-002 / TD-016 遗留，执行计划 P22-R1 最大外部风险）。本设计将 Sprint 2A 显式拆为"**不依赖专家**"与"**依赖专家**"两段，前段先行、后段可顺延。

### 6.1 流程

1. **S2A-1 盘点**（不依赖专家）：完成 §三 阈值盘点表。
2. **S2A-2 评审包**（不依赖专家）：由 §四 生成《阈值确认清单》+ 上下文（Design 输出样例、2.2.1 环境溯源说明、规范引用占位）→ 交付专家。
3. **专家评审**（依赖专家）：逐项签字 / 拒绝 / 暂缓；填写"建议取值区间"与签字列。
4. **签字落地**（双控）：授权角色（非 LLM）将签字结果写入 `verified.json`，带 `verified_by` + `verified_at`；git 留审计痕迹。
5. **回归与验收**（依赖专家后）：重跑 `local_ci.sh` 8/8；新增测试断言"已签字字段不再 pending、未签字维持 pending"（一票否决）；更新 SSOT 与交付报告，部分关闭 TD-002 / TD-016。
6. **治理**：双人复核（专家签字 + 维护者提交）；`verified.json` 历史即审计链。

### 6.2 顺延兜底（关键）

若专家排期不可得：**本设计文档（盘点 + 清单结构 + 机制 + prompt + 测试设计）即为"不依赖专家"段的交付**，可独立验收；"签字转正"实施段（S2A-3 落地）挂起待专家，Design 全程保持 Level 0 `pending`（安全，无编造）。这与 2.2.1 的"真实厂商 DEFERRED"策略同构。

## 七、Prompt 专业化方案

**约束**：不改 `AgentContext` / `AgentResult` 契约；不引入真实工程计算；强化"不杜撰"。

### 7.1 SYSTEM_PROMPT 改进点

- **(a) 环境感知注入**：将 2.2.1 实测字段（`climate_zone` / `prevailing_wind` / `solar_exposure`，仅当 `field_provenance=measured` 时）作为**约束条件**写入用户提示，指示 LLM："高风环境优先内开式"等定性推导，**禁止**输出任何具体风压/厚度数值（pending_verification）。
- **(b) 三方案原型框定**：显式要求输出 `经济 / 舒适 / 高性能` 三原型，各自在"成本—舒适—性能"三角上差异化 `rationale`，并说明取舍。
- **(c) 阈值引用槽位**：允许候选携带 `threshold_refs`（指向 §三 阈值 ID），但**数值本身仍 pending**，由代码在签字后填充。
- **(d) 强化不杜撰**：禁止将任何数值阈值宣称为事实；无实测依据处必须用 `unknown`；不得声称通过结构/法定审查。
- **(e) 溯源提示（辅助）**：提示 LLM 为每个字段标注依据（measured/inferred），但**最终 `pending_verification` 由代码按 ADR §7 计算**，不以 LLM 自报为准。

### 7.2 USER_PROMPT_TEMPLATE 改进点

- `environment_hint` 从纯 JSON 改为"带 provenance 标签"的结构化文本（如 `climate_zone=XX(measured)` / `(inferred)`），使 LLM 区分可信度。
- 保留 `address` / `region_hint` / `vision_hint` / `consultation_hint` 原字段，契约不变。

### 7.3 关联

- 与 TD-016（Vision prompt 专家调优）方法论对齐（prompt 场景化 + 不杜撰），但 TD-016 属独立任务，本 Sprint 仅借鉴不实现。
