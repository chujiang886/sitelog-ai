# BOIP 2.2.3 PDF 方案书增强 — 设计文档

> 阶段：Phase 2.2 Sprint 2B（2.2.3 PDF 方案书增强）
> 身份：BOIP AI 高级研发负责人 / PDF 交付架构
> 关联：2.2.1（Environment evidence）、2.2.2（Design provenance / verified.json）
> 守约：不降低 local_ci 标准、不修改扫描规则、不关闭 pending、不编造工程参数、
> 不设置未经审核 verified=true、engineering_enabled 保持 false。

---

## 〇、目标与约束

把现有「内部草稿级」PDF（`agents/report/generator.py`，reportlab Platypus）升级为
**客户可交付方案书**：结构清晰、数据可信等级可见、AI 推理与工程确认严格区分、
`pending_verification` 状态不隐藏。

**红线（继承 2.2.1 / 2.2.2）**：
- 禁止把 AI 推理（Level 0 inferred）包装成工程确认（Level 2/3）。
- 禁止隐藏 `pending_verification` —— 凡非 verified 字段，PDF 必须显式标「待确认」。
- 禁止任何业务词 + 数值共现（持续满足 `check_fabrication.py`）。
- 不依赖真实外部数据源渲染（mock / disabled / 本地均生成合法 PDF）。

---

## 一、当前 PDF 架构

`agents/report/generator.py`（`generate_project_report(dossier)`）现状：

| 项 | 现状 |
|---|---|
| 渲染引擎 | reportlab Platypus（SimpleDocTemplate / Paragraph / Table） |
| 字体 | `STSong-Light`（CID 字体，中文无乱码），回退 Helvetica |
| 章节 | 封面 → 一、视觉分析 → 二、环境分析 → 三、设计方案 → 四、免责声明 |
| 输入 | `dossier = {project, vision, environment, design}`（各段可为 None） |
| 健壮性 | 缺段显示「暂无数据/待补充」；XML 特殊字符转义；CJK 字体注册失败不阻断 |
| 端点 | `backend/app/api/report.py::POST /api/report/generate` |
| 测试 | `tests/agents/test_report.py`（7 例，仅校验 `%PDF` 合法性 + 不崩溃） |

**不足（本次要补）**：
1. 无「数据可信等级说明」章节，客户无法判断哪些结论是 AI 推理、哪些是实测/已确认。
2. 环境分析仅展示字段值，**不展示 evidence**（来源 `source` / `fetched_at` / `real_data` / `field_provenance`）。
3. 设计方案仅按「方案 1/2/3」平铺，**未对应经济型/舒适型/高性能型三原型**，且不确定每方案「依据/优势/限制/待验证项」分区。
4. 无「已验证 / 推理 / 待确认」三态可视化；免责声明虽提 `pending_verification`，但正文各字段未逐字段标注。
5. 项目基础信息仅地址 + request_id，缺咨询需求（预算/风格/约束）展示位。

## 二、页面结构设计

采用「章节 + 状态徽标（badge）」结构，每节顶部以小标签标注整体可信态：

```
封面（标题 + 项目基础信息）
├─ 一、环境分析
│   ├─ 环境字段表（值 + 单字段可信徽标）
│   └─ 数据来源 evidence（source / fetched_at / real_data）
├─ 二、数据可信等级说明（全局模型 Level 0~3 + 本方案书如何读 badge）
├─ 三、设计方案对比
│   ├─ 经济型方案（经济原型）
│   │   ├─ 依据说明 / 优势 / 限制 / 待验证项
│   │   └─ provenance（field_provenance / threshold_refs / verified）
│   ├─ 舒适型方案（舒适原型）
│   └─ 高性能型方案（高性能原型）
└─ 四、免责与待确认声明（汇总各段 pending + gaps）
```

徽标样式（颜色 + 文字）：
- 已验证（measured / verified，来源可信）：`[已验证]`
- 推理（LLM inferred，Level 0）：`[AI推理·待确认]`
- 待确认（unavailable / 缺数据）：`[待确认]`

> 注：当前系统尚无 `verified=true`（2.2.2 红线），故全文档实际只会出现
> `[AI推理·待确认]` / `[待确认]`，不会出现 `[已验证]` —— 这正是「不包装成工程确认」的可视化落地。

## 三、数据来源展示方案（Environment evidence）

消费 2.2.1 已落的字段（Environment Agent `data`）：
- `field_provenance`：`{climate_zone, prevailing_wind, solar_exposure, noise_level_hint}`
  → measured / inferred / unavailable
- `data_providers`：列表，每项含 `name` / `real_data`(bool) / `source` / `fetched_at` / `status`
- `pending_verification` / `gaps`

PDF 渲染：
- 环境字段表右侧新增「可信度」列，按 `field_provenance` 显示徽标。
- 若 `data_providers` 非空，新增「数据来源」子表：`来源名 | 是否实测(real_data) | 获取时间(fetched_at) | 状态`。
- 若某字段 `unavailable` → 该格显示「待补充」并红标。
- 全程不展示任何真实业务数值（风压/壁厚等保持 pending 文案）。

---

## 四、Environment evidence 展示（同源，单列强调）

独立小节「环境数据溯源」：逐 provider 列出
`名称 / 类型(mock|measured|disabled) / real_data / fetched_at / raw_ref`。
目的：让客户/工程师看到「当前环境结论来自 LLM 推理还是实测源」，透明可追溯。
未配置真实源时（2.2.1 默认 disabled / mock）显式标注 `real_data=false`，
**绝不**渲染为实测。

---

## 五、Design provenance 展示

消费 2.2.2 已落字段（Design Agent `data`）：
- `field_provenance`：`{frame_material, glass_type, dimensions_hint, estimated_cost_tier}` → inferred/verified/unavailable
- `threshold_refs`：`{frame_material: D-TH-01, ...}`（仅引用阈值 ID，数值仍 pending）
- `verified`（来自 `verified.json`）：各阈值 `verified`(bool) / `verified_by` / `verified_at`
- `decision_trace`：三方案原型差异化依据

PDF 渲染（每方案）：
- 「依据说明」= `rationale`（含环境约束引用）
- 「优势」= `pros`；「限制」= `cons`
- 「待验证项」= 该方案涉及但未签字的阈值（`threshold_refs` 中 `verified=false` 者）
  + `gaps` 过滤出 `design_threshold:*` 条目
- provenance 脚注：列出 `frame_material/glass_type/...` 的 `field_provenance`
  与对应 `threshold_refs` ID；全部 `inferred` → 统一标「AI推理·待确认」。

## 六、pending_verification 展示规范

统一标准（落到 generator 常量 `PENDING_BADGE` / `VERIFIED_BADGE` / `INFERRED_BADGE`）：

1. 每个 Agent 段（vision/environment/design）顶部：整体徽标 =
   - `pending_verification is False 且 存在 verified 字段为 true` → `[已验证]`（当前系统不会出现）
   - 否则 → `[AI推理·待确认]` 或 `[待确认]`
2. 每个关键字段：依据 `field_provenance` 渲染单字段徽标（measured→已验证来源；
   inferred→AI推理·待确认；unavailable→待确认；verified→已验证）。
3. 汇总章节（四）：列出所有 `pending_verification=true` 的段 + 其 `gaps`，
   给出醒目结论「本方案书相关结论均需人工核实」。
4. **禁止**任何字段在缺失/推理态下显示成确定性工程结论。

## 七、中文字体方案

沿用既有 `STSong-Light`（CID 字体），所有 `ParagraphStyle` 统一使用该字体；
注册失败回退 Helvetica 且**不阻断生成**（既有 `_ensure_cjk_font` 已满足）。
新增「徽标」用纯色 Paragraph（`[已验证]` / `[AI推理·待确认]` / `[待确认]` 方括号标签
\+ 颜色区分），避免依赖 emoji 字体可能缺失的问题。不引入新字体文件、不增加 PDF 体积风险。

## 八、测试方案

新增 `tests/agents/test_report_provenance.py`（覆盖用户要求的四类）：

1. **三方案数量**：mock dossier 含恰好 3 候选 → PDF 合法；候选数 ≠ 3 时仍不崩溃。
2. **pending 语义**：design 段 `pending_verification=True` 时，PDF 文本含
   `AI推理·待确认` / `待确认` 字样（通过解析 PDF 文本验证）。
3. **provenance**：environment `field_provenance` 含 `measured` 字段时，对应徽标为
   `已验证来源`；含 `inferred` 时显 `AI推理·待确认`；`data_providers` 被渲染。
4. **verified 机制**：`verified.json` 全 `false` 时，全文档不出现 `[已验证]` 绿标；
   构造一个临时 `verified=true` 的副本验证 `[已验证]` 出现（防御性测试，确保机制连通）。
5. **防编造**：dossier 含 `pending_verification` 标记字段，PDF 不把 inferred 渲染成
   确定性结论；`gaps` 中 `design_threshold:*` 条目出现在「待验证项」。
6. **结构关键章节**：PDF 文本含「环境分析」「数据可信等级说明」「设计方案对比」
   「经济型」「舒适型」「高性能型」「免责与待确认声明」等章节锚点。

**PDF 文本提取**：reportlab 默认压缩文本，故既有测试不依赖「字节内搜关键字」。
为满足上述断言，新增 `_extract_pdf_text(pdf_bytes) -> str`（用 `pypdf` 轻量纯 Python）。
若依赖缺失，则该部分测试降级为「仅校验合法 PDF + 不抛」，并在报告中标注。
优先方案：引入 `pypdf`（测试用依赖）；CI 环境已装则直接断言，否则走 fallback。

既有 `tests/agents/test_report.py`：更新 mock 的 design 段 `pending_verification`
为 `True`（对齐 2.2.2 语义），并补 `field_provenance` / `data_providers` /
`threshold_refs` / `verified` 字段，使新测试可断言；旧 7 例保持不变（仍校验不崩溃）。
