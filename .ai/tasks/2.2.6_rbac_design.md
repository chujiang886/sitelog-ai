# BOIP Phase 2.2 Sprint 4B — 2.2.6 RBAC 基础建设（设计文档）

> 身份：BOIP AI 企业平台架构负责人
> 目标：建立 BOIP 企业化权限基础（RBAC 基础设施，**非完整 SaaS**）
> 执行模式：设计 ↓ 编码 ↓ 测试 ↓ 报告 ↓ 停止验收（不进入 Phase 3）

---

## 1. 当前 user / tenant 模型分析

现有模型（`backend/app/db/models/`）已具备多租户骨架：

- **Tenant**（`tenant.py`）：`id`(GUID) / `name` / `slug`(unique) / `status`(active|suspended|archived) / `created_at` / `deleted_at`（软删）。这是所有业务表租户隔离的起点。
- **User**（`user.py`）：`id`(GUID) / `tenant_id`(FK, index) / `email`(unique) / `hashed_password` / `role`(CHECK: `admin|designer|sales|customer|worker`) / `status`(active|suspended|invited) / `created_at` / `deleted_at`。唯一联合索引 `ix_users_tenant_role`。
- **tenant_id 贯穿**：`KnowledgeRule` / `KnowledgeCase` / `Image` / `Project` 等均已带 `tenant_id` 外键，是物理隔离的基础。

**关键结论**：

- `User.role` 是一个**单角色字符串列（legacy）**，仅用于占位/展示，**没有**任何 RBAC 关联表，无法表达「用户-多角色-多权限」。
- 密码现状：`seed.py` 中 `hashed_password="pending_verification"`（Phase 0 占位），**没有**真正的哈希策略。
- `User.role` 的 CHECK 约束不含 `viewer`，但本阶段 RBAC 角色以新建的 `roles` 表为准，**不改动** `User.role` 列（见第 9 节），从而避免 CHECK 约束迁移风险。

---

## 2. 当前认证状态分析

- `backend/app/core/config.py` 已预留 `jwt_secret` 字段（默认空串），但**无签发 / 校验逻辑**。
- 全仓库**无** `/auth/login`、`get_current_user`、`require_permission` 任何实现（grep `jwt|bearer|get_current_user|require_permission` 仅命中 config.py）。
- `uploads` 路由用 `X-Tenant-Id` / `X-User-Id` **请求头**做「伪租户隔离」，匿名可传，非认证。
- `analysis` / `report` 路由**完全匿名**。
- **结论**：当前零认证，RBAC 从零建设；本阶段只在后端落地基础设施，前端登录态属后续独立 sprint。

## 3. Role 设计

引入 RBAC 三表（见第 9 节）：`roles`、`role_permissions`、`user_roles`。

- **`roles`**：全局角色目录，`name` 唯一。本阶段支持三种角色：**`admin` / `designer` / `viewer`**。
- **`user_roles`**：`(user_id, role_id, tenant_id)` 三元关联，唯一约束 `(user_id, role_id, tenant_id)`，支持「每租户多角色」。
- **不改动**现有 `User.role` 列（保留 legacy/兼容）；RBAC 权限判定**以 `user_roles` 为准**。
- 角色语义：
  - `admin`：平台/租户管理 + 全部业务权限。
  - `designer`：业务操作（上传 / 分析 / 报告）。
  - `viewer`：只读（上传/分析/报告的 read）。

---

## 4. Permission 设计

- **`permissions`**：`name` 唯一，形如 `resource:action`。
- **权限目录**：
  - `upload:create`、`upload:read`
  - `analysis:create`、`analysis:read`
  - `report:create`、`report:read`
  - `user:manage`（admin 专属）
  - `tenant:manage`（admin 专属）
- **角色 → 权限映射**（实现中以常量定义，便于 seed 与测试复用）：
  - `admin` → 上述全部（含 `user:manage`、`tenant:manage`）
  - `designer` → `upload/report/analysis` 的 `create` + `read`
  - `viewer` → `upload/report/analysis` 的 `read`
- **权限在登录时解析并嵌入 JWT**，运行时由 `require_permission` 校验，**无需每次查库**（见第 5/6 节）。

---

## 5. JWT 方案设计

- **算法**：HS256，使用标准库 `hmac` / `hashlib` / `base64` / `json` 自实现，**零新增第三方依赖**（与 2.2.5 RAG 的「零新依赖」原则一致）。
- **Payload**：`{ sub, tenant_id, email, role(primary), roles[], permissions[], iat, exp, type:"access" }`。
- **密钥来源**：仅环境变量 `JWT_SECRET`（`config.jwt_secret`）；为空则 **fail-closed**（`AuthConfigError`，拒绝签发/校验）。**不写入代码、不提交**（`.env` 已 gitignore）。
- **有效期**：默认 60 分钟（实现常量，旁标 `# infrastructure-config`）。
- **端点**：`POST /api/auth/login` 签发；`GET /api/auth/me` 读取当前用户。
- **不含刷新令牌**（本阶段基础设施；后续可扩展）。

## 6. FastAPI Depends 鉴权设计

新建 `backend/app/core/security.py`：

- **密码哈希**：`hash_password` / `verify_password`，使用 `hashlib.pbkdf2_hmac(sha256, salt, 100_000)`，存储格式 `pbkdf2_sha256$rounds$salt$hash`；常量旁标 `# infrastructure-config`。
- **JWT**：`create_access_token` / `decode_access_token`（HS256，过期/篡改抛 `AuthError`）。
- **`CurrentUser`** dataclass：`id` / `tenant_id` / `email` / `roles: list[str]` / `permissions: set[str]`。
- **`get_current_user`**：解析 `Authorization: Bearer <token>` → decode → 校验用户存在且 `status=active` 且未软删 → 返回 `CurrentUser`。
- **`require_permission(perm)`**：依赖工厂；校验 `perm ∈ current_user.permissions`，否则抛 `HTTPException(403, "Permission denied: requires 'xxx'")`（**明确信息**）。
- **异常包装**：缺失/非法 token → `401`；过期/篡改 → `401`；均由 `middleware/error_handler.py` 统一为 `{success:false, error:{code, message}}` 信封。

## 7. tenant 隔离策略

- 受保护路由**不再信任客户端 `X-Tenant-Id` 头**；tenant 取自 JWT 的 `tenant_id`（服务端签名可信，防伪造）。
- `uploads` 的写/读均按 `current_user.tenant_id` 过滤（`Image.tenant_id = token.tenant_id`），跨租户访问 → `404` / 无结果。
- `analysis` / `report` 无租户数据表，tenant 隔离体现在「操作归属该 token 租户」；跨租户越权访问由认证层天然隔离（T2 无法用 T1 凭证）。
- **测试验证**：T1 上传图片获得 `image_id`；T2 持自身 token 读同一 `image_id` → `404`。

## 8. API 保护范围

**优先保护（本次加 `Depends`）**：

| 端点 | 依赖 | 权限 |
| --- | --- | --- |
| `POST /api/uploads` | `require_permission("upload:create")` | 写 |
| `GET /api/uploads/{id}` | `require_permission("upload:read")` | 读 |
| `POST /api/analysis/run` | `require_permission("analysis:create")` | 写 |
| `POST /api/report/generate` | `require_permission("report:create")` | 写 |

**新增**：

- `POST /api/auth/login`（匿名）
- `GET /api/auth/me`（需登录，`get_current_user`）

**暂不保护（保持开放，避免一次性扩大面）**：`/health`、`/api/projects`、`/api/agents`、`/api/conversations`、`/api/knowledge`、`/api/vision`、`/api/rag`。

**前端兼容**：现有端点**路径与响应信封不变**；仅未带 token 的调用在**运行时**返回 `401`（前端需后续增加登录态，属独立 sprint，不在本阶段范围）。

## 9. 数据迁移方案

- **新增 4 张表**：`roles`、`permissions`、`role_permissions`、`user_roles`（Alembic 迁移，`autogenerate` + 人工复核）。
- **不改 `User` 表结构**（保留 `User.role` legacy），免去 CHECK 约束 `ALTER` 风险。
- **`seed.py` 扩展**：幂等写入 RBAC 目录（`roles` / `permissions` / `role_permissions`）+ 将现有 `admin` 用户关联 `admin` 角色（`user_roles`）；可选创建 `designer` / `viewer` 演示用户（密码来自环境变量，缺省走开发占位并告警）。
- **升级/回滚**：`alembic upgrade head` / `alembic downgrade base`（CI gate 验证）。

## 10. 测试方案

- **新增 `backend/tests/conftest.py`**：共享 RBAC 测试环境（建表 + 种子目录 + `admin`/`designer`/`viewer` 用户 + token 助手）。因 `tests` 目录被 `check_hardcoded.py` 排除，可安全放置**测试用** JWT secret（非生产密钥）。
- **新增 `backend/tests/test_rbac.py`** 覆盖：
  - 登录成功 / 失败（错误密码 `401`、未知用户 `401`）
  - token 校验（有效 token 解析出正确 `sub`/`tenant_id`/`permissions`；过期/篡改 token `401`）
  - 角色权限（`admin` 可 `upload:create`；`viewer` 缺 `upload:create` → `403` 明确信息）
  - 越权访问（`viewer` 调 `upload:create` → `403`；无 token → `401`）
  - tenant 隔离（T1 上传，T2 token 读 → `404`）
- **改写既有** `test_uploads.py` / `test_api_analysis.py` / `test_api_report.py`：从 `X-Tenant-Id` 头改为携带 `Bearer` token（断言保持不变）。
- **CI**：`bash scripts/ci/local_ci.sh` 目标 **8/8 PASS**，覆盖率 **≥85%**（新增代码须被测试覆盖）。

## 11. 风险分析

- **R1 前端无登录态**：受保护端点运行时 `401`（预期内；契约不变 + 后续前端 sprint 解决）。
- **R2 JWT secret 缺失**：fail-closed（启动/签发报错）；需在 `.env` 配置；CI 经测试 fixture 注入，不依赖提交 secret。
- **R3 权限嵌入 JWT**：权限变更需重新登录生效（本阶段可接受，文档说明）。
- **R4 seed 改造回归**：保持幂等 + 既有 seed 测试覆盖。
- **R5 Alembic 在 SQLite 的兼容**：仅新增表、无 ALTER，低风险；CI gate 验证。
- **R6 覆盖率回归**：新增代码全部由测试覆盖；若 CI 覆盖率 <85% 立即补测试。

### 红线符合性自检

1. 密钥只来自 `.env`（`JWT_SECRET` → `config.jwt_secret`）✅
2. 不提交 JWT secret（`.env` 已 gitignore；测试用 secret 仅 fixture 内）✅
3. `tenant_id` 隔离设计（token 取租户、按租户过滤）✅
4. 未登录访问受保护 API 必须失败（`401`）✅
5. 权限不足明确返回（`403 "Permission denied: requires 'xxx'"`）✅
