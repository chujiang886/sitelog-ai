## 3. 设计要点

### 3.1 StorageBackend 抽象（同构 2.2.1 Provider 抽象）
- `save(key, content, tenant_id) -> key`
- `read(key) -> bytes`：不存在**统一抛 `FileNotFoundError`**（三后端契约一致）
- `delete(key)`：不存在静默忽略
- `resolve_key(tenant_id, sha256, extension) -> "{tenant_id}/{sha256}.{ext}"`

### 3.2 三后端模式映射（满足"外部服务必须支持 mock/disabled/fallback"规则）
| 后端 | 触发 | 用途 |
|---|---|---|
| `local` | `BOIP_STORAGE_BACKEND=local`（默认） | 开发 / CI，沿用 `BOIP_STORAGE_ROOT` |
| `memory` | `BOIP_STORAGE_BACKEND=memory` | 测试 mock，不触碰文件系统 |
| `minio` | `BOIP_STORAGE_BACKEND=minio` + 4 个 `MINIO_*` 环境变量 | 生产可配置 |

- **fail-fast**：未知后端、或 minio 缺环境变量、或 minio SDK 未装 → 抛 `StorageConfigError`，不允许静默降级为空存储。
- **密钥治理**：`MINIO_ENDPOINT/ACCESS_KEY/SECRET_KEY/BUCKET` 仅在运行时从 `.env` 读取，代码内无硬编码密钥；`.env` 已 gitignore（历史确认）。
- **MinIOStorage 防御性**：`read` 将对象缺失（真实 S3Error `NoSuchKey` / fake `KeyError`）统一译为 `FileNotFoundError`，与 `LocalStorage`/`MemoryStorage` 契约对齐。

### 3.3 路径规划与去重（跨后端迁移 DB 不变）
- 逻辑 key 统一 `{tenant_id}/{sha256}.{ext}`：
  - **租户隔离**：前缀 `tenant_id/` 物理隔离不同租户数据。
  - **内容 hash 去重**：相同 `sha256` 同一 key → 幂等写覆盖，天然去重。
  - **迁移安全**：跨后端迁移只搬字节，DB 的 `storage_path`（逻辑 key）保持不变。

### 3.4 上传 API 改造（契约不变）
- 前端仅消费 `storage_path` 元数据字段（图片预览走客户端），上传响应结构未改。
- `uploads.py`：旧"绝对路径 + PIL 落盘"改为 `backend.save(key=backend.resolve_key(...), content=processed.content, ...)`，存**逻辑 key**。
- `vision_tasks.py`：`LocalStorage.read` 兼容旧数据中 `storage_path` 为绝对路径的情况（存在即直接读），保证历史图片仍可识别。

## 6. 架构影响

- **解耦**：图片 I/O 从具体文件系统抽象为接口，未来切换 S3/OSS 只需新增 `StorageBackend` 实现 + 一个 `BOIP_STORAGE_BACKEND` 分支。
- **生产就绪**：MinIO 经环境变量切换，`MinIOStorage` 懒加载 SDK，未配置即 fail-fast，不污染 dev/CI。
- **零回归**：既有上传/视觉 API 契约保持不变，前端无需改动；旧绝对路径数据可读（兼容回退）。
- **可观测**：逻辑 key 统一规划为审计/迁移/租户隔离提供稳定基础。
